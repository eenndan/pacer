Case study · race telemetry · macOS

One GoPro file in. Lap timing, a racing line, deltas and synced video out — checked against a real transponder.

Pacer Studio is a working macOS desktop app that turns a single GoPro recording into a telemetry workstation, using only the GPS and motion streams the camera already writes. No transponder, no data logger, no cloud, no extra hardware.

It is also an engineering showcase, and this page is the case study: what it claims, how each claim is checked, and where the limits are.

There is no download. Source is the only distribution — three commands with pixi. Code signing, notarization, a .dmg, and any platform other than Apple Silicon macOS are deliberate non-goals, not a to-do list.

The claim, and the receipt

Lap timing, validated out-of-sample against a transponder.

Most consumer and phone tools time laps off the video or sample clock, which drifts on the order of 0.1% — enough to quietly bias every lap in a session. Pacer times on the camera's own GPS true-clock, where every GPS sample carries its own timestamp, and interpolates each start/finish crossing along the chord between the two real fixes that straddle the line.

  • ±0.003 smean error against transponder ground truth — essentially unbiased
  • σ 0.0527 sper-lap spread on the cleaner-GPS recording (median DOP 1.4)
  • σ 0.0871 sand on the noisier one (median DOP 2.4) — the hardware sets the floor, not the algorithm
  • 0.13 %that worse σ, as a fraction of a ~68 s kart lap
  • 107 clean laps48 and 59, from 57 and 65 aligned laps, across two recordings

That is a modest sample, and it is the honest one: 107 is the number of laps actually compared, not the span of lap IDs they occupied in a 24-hour transponder log. An earlier version of this page printed “1,150+ laps”, which was those ID ranges added together — wrong by a factor of ten, in the flattering direction.

The pairing is automatic, and it is not circular. No lap is hand-matched: Pacer's per-lap duration sequence is correlated against every candidate window of the transponder log and the alignment taken at the maximum. Because that offset is chosen to maximise r, the r at the winner is an argmax, not an accuracy statistic — so the number worth quoting is the margin. The fingerprint matches at r ≥ 0.99 at exactly one offset and below 0.29 at every other. The session Pacer timed is provably the session the transponder timed.

Honesty as a design rule

A number that will not say how much to trust it is a number you should not use.

The two screenshots below are the ones this project is actually about. Both show a readout disclosing something that would have made it look better to leave out.

  • One spelling of “estimated”. Inferred channels — brake, coast, grip, braking-point hints — carry the canonical (est) marker from a single constant, so the app can never spell it four ways.
  • Provisional timing is demoted, not hidden. On a track with no start line set, lap times render muted and a banner says the timing is unverified until you drag the line.
  • The g-meter's forward axis is the GPS speed derivative, not the IMU, because the IMU's forward axis is vibration-dominated on a kart. The screenshot above says so on screen.
  • Older cameras say so. GPS9 cameras (Hero 9+) time on the camera clock; GPS5 cameras fall back to the video clock and are flagged.

What it does

The analysis a dedicated data logger would give you.

  • True-clock lap & sector timing — the validated core, above.
  • Δ-to-ideal and Δ-to-best — the live readout leads with your gap to the synthesised ideal; the charts are distance-aligned so corners line up.
  • Synced GoPro video — scrub the lap and the footage follows, frame-accurate. A long recording split into chapters is chained onto one timeline: automatically when you drop it, on request from File ▸ Load full recording, which the window offers whenever you are looking at part of one.
  • Dual-lap and cross-recording compare — play two laps side by side, including the best lap of another recording of the same track.
  • A tabbed lap panel — Laps, Corners (per-lap), Stats and Coaching as four full-height pages, on the digits 1–4.
  • A session statistics page — pace distribution, the g-g friction circle, corner/braking/straights reports and the data-trust card. ⌘⇧S opens it full-window.
  • Coaching — every corner ranked by time lost against your own best lap, taken as the median over your clean laps, each with a measured reason and a consistency badge.
  • Session library — a local index of everything you've analysed, charting personal-best progression per track.
  • km/h or mph, and colour-blind-safe cues — both under View, both persisted.

How it's built

One desktop app on a small C++ core, with the correctness argument mechanised.

The interesting part of this project is not the feature list — it is that almost every claim above is held by something that fails a build when it stops being true.

A 1,873-line C++23 core

Everything load-bearing — GPMF ingest, geometry, lap and sector segmentation, GPS9 true-clock timing — lives in pacer/, a clean-room, independently authored implementation. Small enough to read in an afternoon, which is the point.

Generated bindings, gated against drift

The core's types reach Python through litgen-generated nanobind glue. CI regenerates that glue and fails if the committed file differs — so hand-editing the generated layer is not a thing that can quietly happen.

The golden-equivalence gate

Every core-math refactor is proven byte-identical before it lands: a dense fingerprint of a Session's whole public analysis API on a real 11.8 GB recording, compared leaf-by-leaf at eps 0 across 120k+ leaves. A deterministic synthetic session runs the same machinery in CI, so the gate survives on a machine that has never seen the footage. Refactors that cannot move a number, provably don't.

Guards that fail the build, not a style guide that asks nicely

The design system is enforced by tests, each walking the app's own source rather than a snapshot: a dimensional guard (every padding, radius and height in the stylesheet must be a declared step), a glyph guard (every character in a user-visible string must be drawn by the app's own face — Qt silently falls back per character, and eight marks were resolving into five foreign fonts), an inline-style guard (thirty-four scattered setStyleSheet strings are down to five named exemptions, each with prose saying whose decision it is), and a contrast guard holding every text role to WCAG AA and every step of the map's colour ramp apart by more than the CIE76 JND under a deuteranopia simulation. Their exemption lists must each name a decision and are checked in both directions, so a dead exemption is also a failure.

The real app, driven offscreen, on real footage

Dev harnesses in studio/dev/ boot the actual window offscreen on an actual recording. Every screenshot on this page is produced that way, by one command, so a marketing image nobody can regenerate cannot quietly start lying. The suite drives the real widget tree too, and one test boots the app twice at pinned device pixel ratios behind a write tripwire on every write path Python and Qt expose — because the app had been silently re-saving a tracked asset on every launch, and the suite missed it for running at exactly the one DPI that reproduced the committed bytes. 96 CTest registrations run on every change — one of them is this page, checked against the app's own design tokens and its own images.

Built solo, with LLM coding agents under discipline

The implementation is handed to LLM coding agents under a strict protocol: one focused pull request per change, gated by the golden-equivalence check and the full suite before it merges. The rigour above is what makes that workflow safe — the guardrails do the trusting, so the agents can do the typing. The commit history is the honest record of it, including the parts that were measured and thrown away.

Non-goals

What Pacer deliberately isn't.

Stating the boundaries is part of the design. None of these is a roadmap item.

  • Not distributed as a binary. Source is the only distribution. There is no signed or notarized build, no .dmg, no Homebrew formula, and none is planned — this is a portfolio and craft project, not a product looking for install counts.
  • Not cross-platform. The build and the app target Apple Silicon macOS. No Windows, no Linux.
  • Not a live or in-car system. No real-time HUD, no OBD-II or CAN, no in-session telemetry — Pacer reads recorded GoPro footage, after the fact.
  • Not a mobile app, and not a cloud service. Everything runs locally; nothing is uploaded anywhere.
  • Not vendor-neutral. It reads GoPro GPMF. Other cameras and loggers are out of scope.

Build it

A Mac with Apple Silicon, a GoPro file, and three commands.

pixi brings CMake, Ninja, Python, Qt, Catch2 and ffmpeg, pinned by a lockfile, so there is no manual toolchain step. The C++ compiler is the one already on the machine — Apple's Xcode command-line tools.

# 3rdparty deps (gpmf-parser, nanobind)
git submodule update --init --recursive

# environment + editable Python bindings
pixi install

# build + launch on your own recording
pixi run studio -- /path/to/YOUR_RECORDING.MP4
On a track Pacer doesn't know yet it places a sensible start/finish line and flags the timing as provisional; drag the line on the map to where a lap begins and it is remembered for that recording. Read your first lap walks the rest.
